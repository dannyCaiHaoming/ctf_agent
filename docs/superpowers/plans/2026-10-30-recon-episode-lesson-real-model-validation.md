## 1. 用哪些题、为什么这样安排

| 顺序 | 题目与现有来源 | 本批用途 | 必须保留的限制 |
| --- | --- | --- | --- |
| A | Throwback；`llmctf/2015q-web-throwback:latest`；已有 r15 运行材料与完成判定接线 | 从空经验库重新自主解题；产生本批真实 episode 和 lesson | 不导入 r15 解题轨迹、答案或旧 lesson；历史仅供执行者核对部署与可信判定 |
| B | mfw；`llmctf/2016q-web-mfw:latest`；已有本地运行与 `local-mfw-exact-v1` 判定材料 | 新会话、新靶场状态，读取 A 经验；观察调查方法迁移及题目特定方法的适用性核对 | 不把旧 mfw 解法带入；不能因两题都是 Web 就预判 lesson 一定适用 |

题目清单来源为本地三题 practice design §2.1。镜像 digest、材料、controller-side judge 必须在运行准备时按现存文件重新核对；旧 design 中 Throwback “无 oracle”的记载早于 r15，不能直接当作当前状态。只复用经核实的可信判定实现，不能用总是 accepted 的测试 judge。不能完成可信判定接线时明确记录候选／验证层级，不把模型自述升级为 solved。

选择这两题是为了复用已运行过的真实靶场，减少首批环境变量。它们不是新颖性测试，也不是特意构造的同漏洞迁移题。预期可能迁移的方向是公开材料定位、核对材料与当前服务的一致性、用小实验验证假设、根据失败反馈换路；这里只列评审观察点，**不塞入求解 prompt，不指定模型必须生成哪条 lesson**。A 的具体利用前提在 B 中不能直接照搬，是否存在可观察的“不适用”情形由实际轨迹决定。

不把 seizurecipher 加入首批：多加一题增加消耗，不能保证出现更有辨识力的经验消费。如果 A 没有可用 lesson，或 B 没有出现适用／不适用的充分证据，保留“未覆盖／证据不足”，不临时换题、改 lesson、追加第三题凑通过。

### 1.1 执行顺序与数据边界

1. 准备两个单题配置；运行前冻结产品 commit、模型配置、镜像 digest、原始题目材料 hash、所有角色指令和预算。输入仍走 Intake；不加题目专用解法提示。不将旧运行目录暴露给 Agent。
2. 建立独立、初始为空的 `<batch>/runs/experience.sqlite`。A 使用新 workspace、session、容器状态；只有当前题材料可见。
3. A 求解结束，host 保存结果及过程输入，自动执行 episode 整理和 lesson 提炼。核对 A 的来源与质量后，只读备份其已关闭数据库及 hash；不人工增删／改写 lesson。
4. **A 的题后处理结束、数据库关闭后，再启动 B。** 当前产品在整次 run 收尾后才调用题后模型，故不能将 A、B 放进同一次多题 run 来测即时学习。B 用相同 `runsRoot`，保留共享数据库；其余运行状态全部新建。
5. B 通过现有 `ctf_experience_search`／`ctf_experience_read` 自主查阅。正常指令已说明如何查经验；不增加“必须引用某 ID”或“必须采用 A 解法”的定向提示。
6. B 结束后同样自动整理和提炼，检查 B 的 episode 是否保存实际采用结果或反例，以及新 lesson 是否仍绑定 B 自身结果。不能以查阅发生就提前结束验收。

A 提炼失败、为空或来源质量无法支持后题使用时，停止依赖它的 B：报告已完成的步骤与阻塞点，不花 B 预算伪造闭环。A 未 solved 不是自动阻塞；若存在证据支持的局部方法或失败教训，仍可进入 B，但必须保留 unsolved／unknown。

## 2. 怎样证明经验真的被使用

本批由复核者对照普通工具审计、原生消息、当前题产物与数据库做人工取证，不新增产品反馈机制，也不付费调用另一模型裁判。

| 环节 | 必须看到的证据 | 不算通过的情况 |
| --- | --- | --- |
| 过程记录 | A/B 的 `recon_turns` 与原生 message/call、实际工具参数和输出可对齐；抽查一个完整调查回合及存在的失败分支；Solver/Engineer 来源可定位 | 只有摘要或大量行数，无法还原做法 |
| episode | run/challenge、来源 hash、结果引用匹配本次记录；正文保留有效步骤、失败、未知；outcome 与 host 一致 | 整题成功被写成所有分支有效；模型补出未发生的步骤 |
| lesson | 指向 A 的准确 episode ID/版本；when、steps、checks、avoid/limits 能由来源支持；关闭旧会话后仍可展开 | 仅字段合规；空 lesson 被称为已验证可迁移经验 |
| B 实际使用 | 查阅在行动前发生；返回 A 的准确 ID/版本；B 正常交付记录说明借鉴的具体方法及适用依据；随后可定位的工具行动／脚本变化使用了该方法并适配 B 的参数；观察结果进入 B episode | 只 search 命中、只 read、行动后补一句“参考了经验”、只复述原题，或 B solved |
| 适用性边界 | 一条方法经 B 现有线索核对后采用；另一个经验前提经当前材料／实验确认不成立后被放弃或调整，并留下依据 | 为演示拒绝而硬造危险／无意义实验；没有不适用案例却宣称已覆盖 |
| 再积累 | B 的 episode 含实际历史引用及采用结果／反例，B 的 lesson 来源是 B 的 episode；无可提炼内容可明确为空 | 只有 A 的持久化，B 结束后没有经历整理证据 |

每个实际采用案例记录一条最小证据链：

`A lesson ID@version → B read 的 callID/时间 → B 的适用理由 → B 动作 callID/产物 ref → 当前题反馈 → B episode 对应步骤`

需要展开 A episode 才能理解细节时，核实相应 read 和分页返回；本批至少观察一次来源 episode 的实际展开，否则将“来源展开”标为未覆盖。实际借鉴可以发生在 Recon、Solver 或 Engineer，不要求三个角色都表演一次。

这种时间顺序、显式引用和动作对应关系支持“有证据的采用”，不能排除模型本来就知道该方法；要证明增益，必须做 §2.2 对照。没有显式可核对引用，即使动作相似，也只记“无法确认采用”。不读取隐藏推理作为证据。

### 2.1 判定与停止

- **真实闭环通过**：四步均有对应证据，B 至少一条实际采用案例；episode/lesson 无关键编造或结果错绑。适用和不适用、来源展开逐项报告；缺项时只称部分验证，不宣称全部验收通过。
- **组件通过、行为未通过／证据不足**：存储与整理完成，但未检索、未实际采用、无相关 lesson，或缺少反例。按链路定位原因，停止本批；不暗改样本或重跑。
- **发现内容错误或实现失败**：保留原材料与消耗。先离线分析，修复后的真实复跑另行取得预算；不把 R1/R2 的现有确定性故障验证改成付费注错测试。
- 任何阶段触及 token、请求数、时间上限即结束该阶段；显式整体停止不再启动题后调用。普通求解 budget/deadline 结束可在已授权的独立学习额度内整理结果。

### 2.2 可选收益对照（首批不包含）

若以后要回答“经验是否更省、更快”，在另一批添加同一个 B 的空经验库基线 B0：相同题目快照、provider/model、求解额度、指令与工具，新的会话和靶场状态。基线不接触 A/B 的任何经历，关闭其题后学习；与使用冻结 A 经验快照的 B1 比较可验证进展、无效尝试、solve 分层结果、用量和时间。只改变经验可用性。

最好在该对照批次开始前同时固定 B0/B1，而不是从已有多次运行挑最好结果。单对照只能给案例线索，不能给统计收益结论。总成本必须含 A 的学习投入及 B1 的题后成本；不能只报 B1 省下的 tokens。首批结束后才补跑 B0 时须说明时间／配置漂移，不能伪装为预先固定的实验。

## 3. 模型、预算与调用边界（待授权建议）

默认沿用仓库配置 `deepseek/deepseek-flash`，经 OpenCode 和 `@ai-sdk/openai-compatible` 接入官方 endpoint；求解与题后使用同一配置，分别计预算和状态。运行前核实实际解析到的模型、provider、reasoning 选项并冻结；不因失败切 provider。凭据只从既有本地环境载入，不写文档或日志。

### 3.1 额度建议

以下都是**上限而非预计必需消耗，更不保证解出**。token 按当前 host 的 input + output + reasoning observable 口径，包含全部参与角色；不可把缓存输入当免费、不把失败调用排除。provider 计费口径另列，未核实价格前不换算金额。

| run | 求解 token 上限 | 题后 token 上限（episode + lesson 合计） | 小计 |
| --- | ---: | ---: | ---: |
| A / Throwback | 800,000 | 80,000 | 880,000 |
| B / mfw | 1,500,000 | 80,000 | 1,580,000 |
| 首批总上限 | **2,300,000** | **160,000** | **2,460,000** |

预算依据为本地历史 `state/run.json`，本次仅只读提取计数：

- `d-e2e-mfw-20261024-b2/runs/d-e2e-mfw-20261024-b2-1/state/run.json`：297 次准入，739,714 + 146,699 + 178,773 = **1,065,186**。该批为 `volcano-coding/deepseek-v4-1-flash-261017`，模型/provider 和实现版本不同，仅作为量级参考，故不称同配置预测；建议 1.5M。
- 上述路径相对 `/Users/caihaoming/Documents/pentest-agent-run-data/`。新批次按当前实现重新测量，不能沿用旧成功结论。
- 每题题后最多两次模型请求，单次输出上限 4,096。输入还包括有界来源和整理后的 episode；当前准入用 prompt 字节数 + 4,096 作为输入 reserve，不能用“两次短输出”估成 8k 总预算。建议每题 80k 为两阶段共享上限，**不是各 80k**；并非保证任何长度都可完成。暂按 episode 50k、lesson 30k 作规划余量，不新增分阶段硬配额字段。运行记录分别报告两次实际用量。

### 3.2 配套上限与失败处理

| 配置／约束 | A | B |
| --- | ---: | ---: |
| `budget.maxSteps`（全部求解角色模型准入） | 350 | 500 |
| `budget.wallClockMs` | 1,800,000（30 分钟） | 2,700,000（45 分钟） |
| `budget.maxToolJobs`（总 job 上限） | 100 | 100 |
| `budget.reconMaxModelCalls` / `reconClosureReserve` | 60 / 8 | 60 / 8 |
| `learning.wallClockMs` | 300,000（5 分钟） | 300,000（5 分钟） |
| 题后模型请求 | 最多 2 次 | 最多 2 次 |

Recon 在第 52 次附近进入保留收束区、60 为局部硬上限；这不是调查轮数或“必须用满”的目标。自然交回仍由问题是否得到回答决定。上述新增数值均随本批统一授权，不能从历史测试自动继承。

两题各一次 run，无人工重启、无自动换模型、无追加批次。正常在原 scope/预算内修正假设不算重跑。请求失败／响应未知不自动再发；执行前核实 OpenCode/provider 的内部 retry 与实际发送证据，不能把一次 host 准入等同一次 HTTP 请求。若无法确保约定的零重发和成本约束，停在无模型准备阶段报告接口缺口，不用“逻辑只发一次”掩盖实际重试。

现有求解预算和题后预算分别受管，未用完不能互相挪用。provider usage 缺失时记录 unavailable 和已保留额度，不当作零消耗；无法确定剩余额度就停止后续新请求。题后失败保留 pending/failed 和源输入，不改变 solve 结果。两次有界 run 的配置相加构成本批上限，不新建预算服务；未知消耗或用户停止时人工编排不得继续启动 B。
