# CTF Agent 核心設計 v1

記錄日期：2026-10-22（Asia/Tokyo）。

**狀態：第一版核心 design。** 本文定義產品目標、責任、邊界與目標架構；第 3 節列出尚未定稿的待決項。程式現狀、與本文的偏離、已有成果與教訓、清理方向及開發指令收斂對照，見配套的 [現狀、教訓與遷移記錄](2026-10-22-ctf-agent-current-state-and-migration.md)。舊設計、路線圖和主線計劃只作歷史來源，不是本文的上位依據；其中的待辦、凍結軌跡、gate、命令和階段順序均不自動繼承。

**用途與邊界。** 本產品只用於 CTF 比賽與學習題：操作對象限於比賽平台下發、使用者自行部署或明確授權的題目、靶場和附件，所有網路與工具行為受該題 scope 約束（見 1.5）。不用於真實系統、未授權目標或比賽之外的攻擊用途，題面、附件和模型輸出都不能擴大這一範圍。

本文只定義設計，不構成任何執行授權。清理、程式或配置修改、模型運行、自主求解及對題目／平台的操作、Docker 構建、commit 或 push，均需使用者另行明確授權；真實模型運行另須明確目標、模型／provider、批次和 token 預算。

## 1. 產品定位與責任

產品是一套由 OpenCode 承載的多 Agent CTF 系統，最終連同運行環境封裝為 Ubuntu ARM64 Docker 鏡像。OpenCode 負責模型、主／子會話、工具調用循環及上下文管理；Agent 定義、產品運行指令、Skills 和 References 以文檔及配置交付。項目不另造通用 Agent framework。

產品保留九項責任：Coordination、Intake/Triage、Target Recon、Reference、Strategy、Domain Solver、Solution Engineering、Verification、Recovery Critic。Solver 是其中一項，不能代表整個產品。會話安排可以自適應合併簡單職責，職責不能消失；Verifier 必須獨立，Recovery Critic 按持續停滯條件觸發。

| 職責 | 主要工作 |
| --- | --- |
| Coordinator | 組織各 Agent，安排題目、資源和預算，決定繼續、換題或停止，提出平台操作與提交 |
| Intake/Triage | 取得或整理題面、材料、入口與平台狀態，識別類別、能力需求及未知項，交付做題輸入 |
| Target Recon | 分析服務、文件、協議或數學結構，建立有證據的基線與下一步 |
| Reference | 查閱離線知識，給出來源、適用條件及不適用理由；簡單查詢可由工具完成 |
| Strategy | 排序假設，核對前提與反證條件，選擇最小實驗和換路時機 |
| Domain Solver | 使用方法與工具執行實驗、編寫或修正腳本、讀取反饋，產生候選或失敗證據；首批 Web／Misc／Crypto |
| Solution Engineer | 整理解法腳本、命令、依賴和候選提取，形成可驗證產物 |
| Verifier | 在獨立上下文中重放、重算或審計證據，給出驗證結論 |
| Recovery Critic | 持續停滯時指出遺漏、錯誤前提及不同路線 |

取題與做題分開。「取題」是接收和準備可求解的任務，不等同於平台 API 拉題：包括平台題目、已運行的本地／遠端靶場、開發測試中部署的真實靶場，以及使用者直接提供的題面／附件。Intake/Triage 根據來源使用適合的接入能力，確認材料、目標、授權與判定方式；平台 API adapter 只是其中一種工具。做題由 Agent 團隊根據證據選擇 Skill、Reference、工具及實驗腳本，不由宿主硬編碼題目解法。缺少接入或環境能力時，由開發者在自主求解過程之外修補，不把人工解題幫助冒充自主成功。

開發用 `AGENTS.md` 與產品運行用 `AGENTS.md` 必須分開。前者服務倉庫開發；後者描述發布後 CTF Agent 的目標、角色協作、方法與知識使用、運行邊界和成功標準。題目附件中的同名文件不能覆蓋產品指令。

發布後流程：啟動鏡像及注入配置 → 載入產品定義並啟動 Coordinator → **第三步由題目接入 Agent 接題** → 組織解題團隊 → 根據反饋修正或換路 → Engineer 整理候選與 Verifier 獨立驗證 → Coordinator 提出提交、Platform Service 執行 → 繼續其他題目或結束並保存證據。

### 1.1 產品目標與首版範圍

從已授權的題目來源開始，完成材料準備、觀察、假設、實驗、局部修正、換路、候選整理、獨立驗證與可信完成判定。支持 Web／Misc／Crypto，涵蓋單題、多題、多 flag、離線計算、互動連線和長作業；不承諾首版完整覆蓋 Pwn、Reverse、Mobile 等其他領域。平台接入與直接靶場／附件接入同屬產品能力，不以某一平台、特定題目成功或舊里程碑作整個產品的定義。

自主解題要求由 Agent 選擇方法並操作真實工具；開發者可以在 run 外準備環境和接入適配，但不能向做題上下文補入專屬解法、答案或未授權材料。一次公開題成功只證明該題，不能據此聲稱通用解題率或排除訓練污染。

### 1.2 Agent、文檔與程式的責任界面

Agent 文檔描述角色目標、協作、決策和交付要求；Skill 提供可按需採用的方法；Reference 提供帶來源與適用條件的知識。產品 `AGENTS.md` 描述共同運行約定，不把所有角色、方法和知識全文塞入同一指令。OpenCode 承擔模型調用、會話、工具循環與上下文管理。

宿主程式保留必要的確定性責任：可信任務身份、材料來源、路徑與內容版本、會話綁定、scope、預算、資源狀態、產物封存、候選有效性、平台副作用與權威結果。這些是 Agent 使用的能力與約束，不是另一套決定解題路線的 Solver。CLI 只負責啟動、配置與狀態呈現，不能再成為硬編碼的 Agent 編排器；入口形態、文件分區與本地調試流程以 [入口與本地調試詳細 design](2026-10-22-design-v1-entry-local-debug.md) 為準。既有 Supervisor、State、Platform、Tool 等名稱只代表責任，不要求各自保留一個套件或服務。

Agent 交接只攜帶下一步必要資訊：目標、輸入與證據引用、觀察和假設、已否定路線、未解問題、產物與建議下一步。身份、hash、計數和可信狀態由宿主填入。簡單讀取、腳本修錯不重新跑整個團隊；機制前提被反證或資源取捨改變時，再回到 Strategy／Coordinator。普通 404、登入失敗、語法錯誤和無效假設是可解釋的反饋，不自動升級為工程故障。

交接資訊保留與局部修正的細節，以 [交接連續性詳細 design](2026-10-24-design-v1-agent-handoff-continuity.md) 為準；離線核對已定位 Coordinator 的修正語義及 Verifier 未取得 blocker 就猜測修正的問題，最小待實作範圍限於這兩個角色，其餘一般交接約定仍為候選。尚未改變產品行為或證明效率改善，不放寬獨立驗證、版本綁定或可信完成要求。

### 1.3 獨立驗證、提交與成功標準

候選必須固定精確值、提取方式、相關腳本／輸入／證據與有效條件。Engineer 整理可驗證產物；Verifier 使用獨立上下文，按候選性質選擇以下方式，不以另一個角色名稱或隨機 session ID 假裝獨立驗證。

| 驗證方式 | 適用情形與要求 |
| --- | --- |
| 安全重放 replay | 可安全重跑的解法；核對實際產物與候選 bytes，不因驗證重置遠端狀態或消耗限次資源 |
| 本地重算 recompute | 可由保存的輸入重算；檢查推導／提取鏈、編碼和最終值 |
| 證據審計 evidence_audit | 一次性、限次或依賴原連線狀態；檢查完整相關記錄、先決狀態、順序及提取位置，說明不可重放原因 |

缺關鍵證據只能記為 inconclusive 或 rejected。候選、實際依賴或相關實例／連線狀態改變時驗證失效；無關臨時文件變動不使整題結論失效。Verifier 不持有提交、提示或實例修改權限。Coordinator 依仍有效的驗證提出提交，由受控平台／oracle 能力執行，不能由模型自述改成成功。

只有取得真實候選、獨立驗證通過且可信平台／local oracle 確認整題完成，才記為 solved。多 flag 的部分接受為 partial；沒有可信完成判定的已驗證候選仍為 candidate_only。HTTP 200、外觀像 flag、工具返回成功、模型聲稱完成均不足。平台拒絕後把具體反饋交回團隊；提交結果未知則保留 unknown，不盲目重發。

運行狀態、解題進度、資源／清理狀態與最終結果分開記錄。未解出、證據不足和基礎環境無效需要可區分，但不沿用舊文檔整套 enum 或 schema 作為必須實作的前提。

### 1.4 預算、平台操作與恢復

同一產品 run 內的多 Agent 共用已授權預算，不因建立子會話、重試或恢復重新計數。模型成本、時間、工具資源與平台配額分別管理；平台的實例上限由 adapter 能力決定，不把某平台的三實例限制寫成通用規則。首版可限制單一配置只運行一個 active run，題內並行度另行管理。

宿主記錄實際可觀察用量與 provider usage，後者不可得記 unavailable。可觀察 token 限額與帳號供應商額度不同；在途回應可能越過本地門檻，不能宣稱精確硬封頂。預算說明或上限澄清不等於啟動新批次的授權。

操作按實際副作用處理：可重建的本地操作、可安全重試的觀察，以及提交／提示／實例管理／限次互動等受保護操作。HTTP 方法不足以判定副作用，例如取列表也可能啟動平台計時。受保護操作在送出前保存意圖，區分傳輸狀態和業務結果；未知結果先對帳，只阻止受影響操作，不把所有正常工具調用變成審批流程。

保存可恢復的任務目標、下一動作、已否定路線、必要原始證據引用、腳本、活動句柄／讀取游標和剩餘預算。優先復用 OpenCode 上下文管理，不另外建立模型摘要循環。摘要不能代替原始證據。首版故障恢復可採停止舊作業再重建的方式；確認舊執行已停止後才重啟，不承諾接管存活 PTY／瀏覽器／長作業。恢復不重置預算、平台時間或已確認得分；實例重建只失效依賴該實例狀態的成果。

### 1.5 工具、知識、資料與隔離

解題工具應覆蓋受管文件與二進位／歸檔讀取、腳本編寫和執行、HTTP 與會話、必要瀏覽器、PTY／TCP、長作業取消和增量輸出。Web、Misc、Crypto 依實際需求選擇預裝工具，不以工具清單代替可用性驗證。長作業輸出應及時可讀，不能等待整份 artifact 封存；截斷、缺失與續讀游標明確呈現，僅封存支撐候選或排障所需內容。

離線知識在發布／run 開始時固定版本，帶來源與適用說明；新經驗經 run 外審核後再發布，不在求解中熱更新解法。正式做題不使用公共搜尋、GitHub、線上文檔或 writeup，不安裝依賴。題面、附件、Reference 與模型輸出均不能擴大 scope 或升級為產品指令。

OpenCode 工作目錄由宿主為每次 run 新建並控制，只含宿主寫入的配置與產品資產副本。題目材料、解包產物和 Agent 寫入的文件不得出現在其根部；任何 SDK 請求不得以題目工作區或其他非宿主建立的目錄作 `directory`。固定版本即使禁用專案配置，仍會載入該位置 `.opencode/` 下的角色、Skill、命令，並執行其中的插件與自訂工具，而插件所在進程持有控制憑據。啟動器在工作目錄含 `.opencode/` 或非宿主寫入的條目時拒絕啟動，Agent 寫入權限不覆蓋工作目錄。這是硬性邊界，不以過濾題目文件代替；實測依據與細節見 [A／B 詳細 design](2026-10-22-design-v1-ab-product-assets.md) 第 3 節。

平台 Token、provider key、VPN 憑據及 oracle 私有答案不進模型上下文、工具 job 或模型可讀日誌。題目必要登入資料與控制憑據分開處理；能以受管會話引用完成的操作不暴露秘密值。大量輸出留在受控資料區按需讀取，不全文塞入上下文。

瀏覽器使用題目隔離的 profile，導航、請求、WebSocket 和下載都須遵守 scope，不能攜帶平台控制憑據。腳本和其他網路工具同樣受限，不能只攔自訂 HTTP 工具就聲稱全面隔離。開發機執行不證明容器隔離；產品以非 root、受控檔案和實際網路限制運行，不掛宿主 Docker socket，也不宣稱能安全承載任意惡意逃逸程式。

### 1.6 發布環境與能力驗收

產品交付 Ubuntu ARM64 鏡像，包含固定 OpenCode／插件版本、產品文檔、Skills／References、必要工具鏈與瀏覽器依賴。基礎鏡像和依賴版本可追溯，啟動不依賴開發機路徑或臨時下載；運行狀態與證據使用持久資料目錄，秘密運行時注入。VPN／網路連通從實際容器工具驗證；宿主連通或模擬 ARM64 不代表原生 ARM64 可用。題目環境與產品鏡像分開準備。

驗證分開陳述：文檔／配置可載入、確定性工具接線、真實角色協作與方法使用、候選獨立驗證、權威整題接受、發布鏡像可運行。fixture 不證明模型解題能力；host-dev 成功不證明發布形態成功。真實測試與日常做題使用同一產品入口，不維護測試專用 Solver。

正式評估前固定題集、初始狀態、模型、知識／工具版本和預算；不把已有平台得分或人工進度算成自主成果，不在失敗後刪除超時／缺能力／未解題目來縮小分母。單題驗證和多題成功率評估是不同證據。正式成功率門檻尚未定稿（見第 3 節）：須先以真實基線校準，在正式評估前與使用者確認並記錄，不能 run 後放寬。舊設計的門檻只作歷史參考，見配套記錄第 4 節。

## 2. 目標架構

以下 A–H 描述目標能力，不要求保留現有程式實作；優先復用 OpenCode 原生能力，必要控制功能以清楚的最小實作提供。

### A. 獨立產品運行資產包

集中產品 `AGENTS.md`、OpenCode 配置、完整角色定義、Skills 和 References；開發用 `AGENTS.md` 留在倉庫根目錄。Coordinator 作發布入口的 primary Agent，其餘按責任配置，Reference／Critic 按需使用。

透過原生配置目錄或 instructions 載入產品文件，不再把正文轉成宿主常數。固定版本可在禁用專案掃描時載入明確指定的 instruction 文件，無需犧牲隔離。

產品資產目錄的位置與布局、載入方式及版本記錄，以 [A／B 詳細 design](2026-10-22-design-v1-ab-product-assets.md) 為準。

### B. 原生 Skill 與受控 Reference

保留已審核 Web 方法，補原生 metadata，納入受信任發現範圍，使用原生 `skill` 按需載入，移除全文預載。對已發布知識提供受控只讀訪問，保存來源與版本。

區分 Skill 附屬短 Reference 與共用知識目錄。前者優先接通；後者以唯讀目錄發布並經限定路徑的讀取規則查閱，固定版本的本地 `references` 配置無可觀察效果，不作為載入路徑。運行時不使用 Git 拉取。Skill metadata、Reference 接法、權限與 `rg` 依賴的細節以 [A／B 詳細 design](2026-10-22-design-v1-ab-product-assets.md) 為準。原生目錄可見性不能替代人工審核、固定快照和來源記錄；不為未發生的查詢需求另設檢索服務。

只准讀已發布知識根目錄並核對實際路徑，不放行整個含配置／憑據的控制目錄。題目資料仍走受管工作區工具，避免其中的指令文件被自動提升為產品指令。

### C. 原生多 Agent 與薄控制層

優先用原生 `task`，由 OpenCode 管理子會話和模型循環。宿主核實父子關係及角色，在首次模型／工具操作前完成綁定，分配工作區與能力，統一計量預算，處理取消、到期和交接證據。

既有前台 task 的首次綁定與准入已驗證；G 異步分派、完成喚醒與等待中停止已在隔離原型完成聯合無模型驗證（G §9、C §6.2），並已接入主區（G §9.2）。父下一輪准入不得清理仍在啟動的 pending，父 idle 不等於 run 完成。若原生 `task` 確實不滿足邊界，再提出有界 SDK 接線方案或設計 blocker，不自行另造分派循環、不維護 fork。控制服務、插件接線、會話綁定、預算准入與角色能力的細節以 [C 詳細 design](2026-10-23-design-v1-c-control-service.md) 為準。

#### C.1 原生 task 的綁定時序（已定稿：採原生 `task`）

**已於 2026-10-23 經無模型驗證，採用原生 `task`；機制、驗證結論與保留見 [C 詳細 design](2026-10-23-design-v1-c-control-service.md)。** 這只證明綁定時序、權限與計量接線，不代表多 Agent 協作效果已驗證。以下保留原始的驗證要求作為該結論的依據說明。無模型驗證需在固定 OpenCode 版本上觀察真正的子會話建立與公開攔截點；以本地確定性替身代替 provider，阻止任何真實模型請求。不能只用手寫事件或假的 session ID 驗證自己的假設。

驗證要回答：宿主能否在子會話第一次模型請求及工具操作前，取得可信父子關係與實際角色，完成 run／題目／工作區綁定和共享預算准入；角色是否能被呼叫參數冒充；未綁定或已取消的子會話是否確實被阻止。並行子會話不得重複花用同一份剩餘預算；取消、deadline 和用量回收必須覆蓋全部子會話。這只驗證時序、權限與計量接線，不驗證模型協作效果或 provider 真實計費精度。

| 驗證結果 | 設計去向 |
| --- | --- |
| 公開接口能在必要操作前完成綁定和准入 | 採原生 `task`；插件只做身份核實、能力限制、預算及停止接線，Agent 文檔描述分派與交接 |
| 原生 `task` 無法滿足上述時序 | 不放行未綁定子會話；改評估有界 SDK 接線：由受管分派工具接收 Agent 選定的角色與任務，透過公開 SDK 建立會話，完成綁定後才啟動 OpenCode 會話。決策仍由 Agent 作出，模型與工具內循環仍由 OpenCode 執行 |
| SDK 也不能先綁定再執行，或不能隔離 Verifier／傳播取消及預算限制 | 明確列為架構阻塞，報告缺失接口與可選產品範圍調整；不另寫 provider 循環、不維護 fork，也不把單 Solver 降格替代稱為完整多 Agent |

G 解題子任務採異步返回可信引用、後續自動交付同一邏輯任務的契約。固定映射為 OpenCode 1.19.3 公開背景開關與原生 `task(background=true)`；真實安裝版 schema、自然父喚醒／停止及最小 C 關聯接線已在隔離原型驗證。C 用宿主執行 ref 經原生 description／synthetic 通知傳遞，另核對 SDK parentID／agent、原生 callID／metadata；首次回覆、後續結果及准入狀態分開，不用模型自由文字授權。此片不啟用 SDK 備案，原生能力不足時的通用去向仍依 C §7；不增加通用排程或 provider 循環。版本、條件與未驗邊界以 G §7.2.2／§9 為準。

### D. Agent 使用必要的候選與驗證能力

為跑通一道題所需的產物交接、固定候選、獨立驗證及可信完成接口，細節以 [D 最小版詳細 design](2026-10-24-design-v1-d-candidate-verification-minimal.md) 為準。角色責任與本節邊界不變；接口一已經無模型原型及主核對，按首題最小邊界已接入主區並完成無模型驗收；H1 完整條件未通過及 H5/H7 限制仍保留，接口二一次固定候選與解法包已接入主區並通過無模型回歸，第三接口已按首題材料交接／執行關聯最小邊界定稿，V3持續輸入完整性及未聲明依賴保留unknown；主區接入狀態見子文件§5，第四、第五接口已按核對來源接入主區，完成定向43/43、全套403/403及同源十案無模型驗收；真實裁判通道與秘密隔離部署仍有缺口。具體決策與限制見子文件 §3–7.1，不代表 D 已完成或真實題目已 solved。

Engineer 整理解法和提取方式，由服務固定產物；Verifier 使用獨立 OpenCode 會話及必要證據，選擇驗證方式，不繼承 Solver 完整推理上下文。現有重放／計算檢查作為驗證工具；Coordinator 根據有效驗證提出提交，Platform Service 執行。

Agent 自述不能替代證據校驗。需保留的是獨立驗證與可信提交的能力和邊界，不是現有服務的全部類別、流程或歷史測試；現有檢查只在符合本節邊界時復用。

### E. 分開取題與做題

發布流程第三步為 Intake/Triage 接題：先辨識來源，再取得／整理題面、附件、目標及狀態，交給統一做題入口，Coordinator 再組織解題團隊。不得要求每道題都有平台列表、啟動 API 或提交 API，也不為靶場製造一個偽平台。

| 題目來源 | 接入工作 | 完成判定與限制 |
| --- | --- | --- |
| CTF 平台 API | 透過 adapter 取得列表、題面、附件、實例和平台狀態；按平台能力管理計時與提交 | 使用平台權威回應；不存在的能力標明缺失，不臆造接口 |
| 已運行的本地或遠端靶場 | 接收獲授權地址、必要題面和材料，確認可達性、協議及 scope；不假設入口一定是 HTTP | 有可信 local oracle／靶場完成接口才可標 solved；沒有則保留已驗證候選或其他明確結果 |
| 開發測試所用真實靶場 | 由開發者或獲授權的外部準備工具部署，將公開題面、附件和實際入口交給同一 Intake 路徑；記錄版本與準備／清理方式 | 部署資料、私有 flag 和 oracle 留在做題 Agent 之外；部署成功不代表解題成功 |
| 直接提供題面與附件 | 接收文字、文件或歸檔，保留原始材料來源；可無網路目標，支援 Misc／Crypto 等離線任務 | 確認判定方式；缺材料或缺裁判分別記錄，不強制偽造 target URL |

本地靶場與直接提供題面／附件兩種來源的運行配置、材料固定與 Intake 接入工具，細節以 [E 最小版詳細 design](2026-10-23-design-v1-e-intake-minimal.md) 為準；平台 API adapter 與開發測試靶場部署不在其範圍。

Intake 交付共同必要資訊：原始題面和材料來源、實際可用目標（可為空）、授權範圍、實例是否已就緒、可用完成判定及缺失項。沒有的字段保持未知或不適用，不要求使用者為簡單靶場手寫一份繁複 manifest，也不把平台管理信息全部塞給 Solver。

測試需要區分確定性 fixture 與真實靶場。fixture 只證明裝配；真實靶場在相同產品做題入口上驗證能力，不使用另一套測試專用 Solver 或暗示解法。優先接通本地／遠端直接靶場及附件輸入，再擴展平台 API 來源。HTTP、TCP 或其他已支持協議由 Recon 識別，不默認把題目歸為 Web。

題目部署與產品 Docker 鏡像是兩個邊界。產品鏡像提供解題環境，不默認把所有靶場打進鏡像，也不默認向 Agent 暴露宿主 Docker socket。靶場啟動、停止、重置只透過另有授權的準備／管理能力，不能在求解中為配合假設擅自改題。平台憑據不進模型，做題 Agent 不擴張平台權限；沒有 oracle 仍可探索和驗證候選，但不得宣稱 solved。

### F. Docker 可交付佈局

固定產品資產與工具隨鏡像發布；工作區、證據和狀態放持久資料目錄；秘密在運行時注入；OpenCode 配置／快取有明確運行目錄，不依賴開發機路徑。

沿用 Ubuntu ARM64 目標，驗證冷啟動不下載依賴、工具可用及網路／文件邊界。OpenCode 初始化涉及配置目錄依賴準備，封裝時要處理，不能把目錄設為唯讀便宣稱可運行。

### G. 首版工具集、領域入口與執行邊界

工具集按能力定義，具體套件及版本在鏡像實作時選定。每項能力要同時有 Agent 可調用入口、實際執行環境和必要邊界；只有文件列名或工具註冊不算可用。優先使用 OpenCode 原生文件／搜尋／編輯能力；只有原生入口不能滿足路徑、身份、輸出或資源限制時才增加薄包裝，不為每個系統命令另造工具。

| 能力 | 首版方向 | 邊界與待決事項 |
| --- | --- | --- |
| 文件、搜尋與腳本編輯 | 讀取題面／附件、二進位片段、搜尋材料；在所屬工作區建立及修改腳本；解包保留來源關係 | 原始材料唯讀，衍生文件可寫；拒絕越界路徑及符號連結逃出；不能讀控制憑據、oracle 私有資料或其他題目 |
| 批次腳本執行 | 預裝 Python、Node 及必要 shell／基礎工具；回傳作業句柄、退出狀態及可續讀輸出 | 固定工作目錄、受控環境變數、時間／CPU／記憶體／輸出限制；取消終止整個作業。原生 shell 能否受同等限制待驗證，否則走受管 job 入口；運行時不安裝依賴 |
| HTTP 與會話 | 支持方法、請求內容、重新導向、Cookie／會話與完整回應的受控讀取 | 每次實際連線和重新導向遵守 scope；會話按題隔離，不暴露平台控制憑據；普通 HTTP 錯誤回給 Agent 判斷 |
| 瀏覽器 | 提供頁面導航、DOM／畫面觀察、互動及必要下載；優先評估預裝 Playwright／Chromium | 每題獨立 profile；頁面子請求、WebSocket 和下載同受網路與文件邊界約束。具體瀏覽器接口與 ARM64 依賴待定；不用 HTTP fixture 冒充瀏覽器驗證 |
| PTY／TCP | PTY 承載需持續互動的本地程式；TCP 支持授權服務的連線、讀寫、關閉及增量輸出 | 句柄綁定題目、會話和實例世代；連線有超時與取消；不得用新連線假裝重放一次性狀態。PTY 與 TCP 是不同能力，不互相代替 |
| 長作業及觀察 | 支持啟動、狀態、增量讀取、輸入及取消；完成後能交回等待中的任務 | 無須用模型持續輪詢；輸出有界且可續讀，缺失明示。G 批次 job 同次工具等待終態；Coordinator 異步分派後取得可信引用，後續結果自動交付同一邏輯任務，不改寫首次工具回覆。原生 early ref、其他任務的完成通知與受管 stop 提供本切片控制機會；固定公開接線已驗，不引入通用訊息平台 |
| 領域依賴 | Web：HTTP、解析與瀏覽器；Misc：文件／編碼／歸檔及按需預裝的媒體處理；Crypto：數值、符號計算及必要約束求解庫 | 具體套件、版本和大型工具是否納入按需求及 ARM64 實測決定；缺能力顯式返回，不臨時下載、不假稱全領域工具已齊備 |

Web／Misc／Crypto 由 Intake 的材料與能力判斷交給相應 Domain Solver 定義和 Skills，共用上述工具與候選驗證接口。分類不確定時可以跨領域協作；離線題可沒有網路目標，不能默認歸成 Web。不是新增三套 CLI 或三個硬編碼求解循環。

網路限制須在執行環境覆蓋腳本、瀏覽器和直接 TCP，不能只靠 Agent 指令或自訂 HTTP 工具攔截；工具看不見平台管理端及私有 oracle。具體網路隔離方案是發布前待決項，在其實測通過前只可陳述開發環境的有限能力，不宣稱產品 scope 已全面強制執行。

首版解題工具細節以 [G 詳細 design](2026-10-23-design-v1-g-solver-minimal.md) 為準，目標不變、整體未定稿。既有產品 C/RPC 接線及失敗證據保留；七項未定問題已完成獨立無模型調查並回寫 G。長作業／停止已選定統一契約：Solver 同次等待 job 終態（移除 wait_ms），Coordinator 異步取得任務引用並可停止，結果自動交付同一邏輯任務。原生背景公開映射、pending、父 idle 收束、自然停止與完成准入的隔離原型聯合驗證已完成；六個完整 runtime 情境與確定性邊界分開記錄，舊失敗不改標通過。主線已接入並做無模型驗收（G §9.2）；真實模型能力尚未驗。OS 採每會話容器、網路採 namespace 預設拒絕底層；可信佈建及完整 origin／協議 scope 仍未定，不隱含授予產品 Docker socket／root。配額、受保護操作與 Verifier 重放的剩餘契約見 G §10，條件與證據見 §9。主工作區已接入 G 已定部分，D 直接依賴及延後工程保持未完成；沒有本批真實模型運行。

### H. 控制層最小能力接口與角色權限

以下是**語義接口草案**，名稱用來界定契約，不是要求新建同名服務、JSON 動作協議或全部自訂工具。角色能力的執行方式與首版工具對應見 [C 詳細 design](2026-10-23-design-v1-c-control-service.md) 第 5 節。原生 `task`／`skill`／文件工具能滿足契約就直接使用；必要控制透過公開插件／SDK 和小量受管工具接入。角色可調用的能力如下，未列能力預設不授予。

| 能力接口 | Agent 提供的意圖／輸入 | 宿主提供的結果及約束 |
| --- | --- | --- |
| 任務狀態讀取 | 所需狀態或已獲授權的任務引用 | 返回題目、scope、可用能力、剩餘預算及進度；不包含控制秘密或任意全局任務查詢 |
| 任務分派／交接 | 允許的角色、目標、必要材料／證據引用及任務結果 | 依 C 建立真實會話並綁定身份，返回句柄／結果；Agent 不能指定可信身份、提高權限或增加預算 |
| 題目接入 | 已配置的來源引用、待取得題目或直接材料／目標 | adapter 取得公開材料與平台狀態，宿主固定來源、身份和 scope；不能由題面改寫授權範圍 |
| 知識與工作區讀寫 | Skill 名、知識或材料路徑／範圍、需寫入的工作文件 | 原生按需載入及受限文件操作；已發布知識、原始材料唯讀，工作文件按角色／題目授權 |
| 實驗與作業控制 | G 中的請求、腳本、互動輸入或句柄 | 執行、返回觀察、狀態和續讀位置，支持取消；句柄不能跨題冒用，費用與資源由宿主計量 |
| 產物發布／候選登記 | 要固定的工作文件、候選值或其提取位置、相關證據 | 宿主生成不可變引用與內容版本；登記只產生未驗證候選，不更改 solved 或發起提交 |
| 驗證結果登記 | 候選引用、驗證模式、檢查結果和證據／不足項 | 僅接受綁定 Verifier 任務的結果，核對候選與依賴一致性；記錄 verified／rejected／inconclusive，不把角色自述當證據 |
| 平台操作請求 | 提交的候選引用，或已授權的提示／實例操作意圖 | 僅由控制服務持有憑據並執行，檢查驗證有效性、scope、配額與未知副作用；返回業務回執，不讓 Agent 直接寫權威結果 |
| 任務停止／資源釋放 | 要停止的已授權任務或資源引用及原因 | 按可信直接分派關係核實後先撤銷，再回收資源及 abort 會話，分別保存結果／unknown；到期和預算停止由宿主主動執行，不依賴 Agent 自願調用 |

| 角色 | 允許的能力 | 不授予的關鍵能力 |
| --- | --- | --- |
| Coordinator | 全局授權範圍內的狀態、分派／交接、結果與知識讀取、平台操作請求、子任務停止 | 默認不直接做目標實驗、不簽署驗證結果、不直接讀控制秘密 |
| Intake/Triage | 題目接入、材料整理與必要工作區寫入、來源狀態和受限可達性檢查、知識讀取、交接 | 不自由執行解題腳本、不提交候選或管理實例；接入 API 若有啟動計時等副作用，須經宿主既有授權檢查 |
| Target Recon | 題內材料／知識讀取、工作區寫入、G 中任務允許的觀察與實驗、證據發布、交接 | 無平台管理／提交、無驗證簽署 |
| Reference | 已發布知識查閱及任務提供的必要材料讀取、帶來源的交接 | 無目標網路、腳本執行、材料修改或平台操作 |
| Strategy | 狀態、材料／觀察／知識讀取，提出假設與實驗任務交接 | 默認不直接執行實驗或新增子 Agent；分派交 Coordinator |
| Domain Solver | 題內材料／知識、工作區編輯、G 中被授予的實驗與作業控制、產物發布及候選登記、交接 | 無平台管理／提交、無驗證簽署、不自行生成新 Agent 或提升能力 |
| Solution Engineer | 已交付材料與證據讀取、專屬工作區編輯、本地執行、產物發布與候選修訂 | 默認無目標網路；確需重新採樣時交回 Solver，避免整理產物時重複副作用 |
| Verifier | 固定候選／材料／證據讀取、獨立工作區和本地重算，按驗證模式獲授予的安全重放能力、驗證結果登記 | 不繼承 Solver 私有推理、不改原候選或其證據、無平台提示／實例管理／提交；不可安全重放時只審計證據 |
| Recovery Critic | 必要狀態、證據、已否定路線與知識讀取，交付不同路線建議 | 默認無實驗、寫入候選、分派或平台操作 |

這是默認分工，不要求每個責任都建立獨立會話；簡單職責合併須在派發時由宿主明確綁定並取所需最小能力，不允許 Agent 自稱兼任角色取得權限。Verifier 始終獨立。工具可見性與執行許可都要約束，真正執行仍以可信會話、run、題目 scope 和角色核對，不能只依賴模型傳入的 role 字段。

所有接口共同返回可理解的結果、必要證據引用及錯誤類別。區分缺能力、越界、資源不足、一般工具失敗和結果未知；不讓工具錯誤默默結束求解，也不由模型維護 host 已知字段。工具註冊名、精確參數及原生／受管入口映射在 C 和 G 的可行性核對後定稿；上述能力責任與權限邊界不留空，也不以新增完整 schema 框架作前置。
