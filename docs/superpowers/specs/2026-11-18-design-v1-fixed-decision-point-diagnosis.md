# 固定決策點診斷：分清方法發現、內容、承接、措辭與模型能力

**狀態（2026-11-18）：** 進行中。離線核對（§6）與合成案例模型對照（§7，48 次執行）已完成：Q2–Q5 都沒有成立；同 session 續接時工作簿常不更新，與離線核對的方向相反，兩者並列待查。換模型的 Q6 對照未授權。

本文是[團隊決策上下文 §7.1](2026-11-07-design-v1-team-decision-context.md#71-行為歸因分清沒看到沒理解與做不到) 的詳細子文件，細節以本文為準。方向依據見 [B §7](2026-10-26-design-v1-b-method-generalization-and-efficiency.md#7-方向与优先序)：主驗收是方法選擇與連續執行，本文負責在動內容、接口、角色契約或模型配置之前，先定位失敗在哪一層。

## 1. 結論與邊界

**結論。** 不再用「改一句提示 → 跑整題」判斷改動是否有效。整題包含模型波動、路線選擇、材料理解、工具執行與時間分配，3 次 `ezoj` run 只支持時序，分不出原因（[B §7.2](2026-10-26-design-v1-b-method-generalization-and-efficiency.md#72-python-运行时阻断归因)）。改為在固定的決策點上一次只改一個條件做比較：先做不需要模型的離線核對，再決定是否值得申請模型對照。

**邊界。**
- 只分析做題流程與角色能力。工程 session 不用模型做滲透或利用，不連題目服務，不重放請求。
- 需要模型的對照只用無害的合成案例（本地資料解析、格式轉換、版本行為差異、程式除錯），不帶題目上下文，不含利用內容；另行授權模型／provider、批次與 token 上限。
- 不新增角色、知識服務、評分器或 gate；離線產出只放計數與結構化欄位。

## 2. 要回答的問題

決策點指一次會改變後續走向的角色動作：Solver 寫或升級假設、交回；Coordinator 派單、續接或新建、停止。對失敗的決策點，依序回答：

| 編號 | 問題 | 成立時的含義 |
| --- | --- | --- |
| Q1 沒看到 | 所需條目、證據 ref 或方法名，當時有沒有出現在該角色的上下文中 | 呈現或綁定缺陷，不歸因模型 |
| Q2 發現 | 方法可用、適用條件已出現，卻沒有載入或沒有讀到需要的 Reference | 發現與觸發問題 |
| Q3 內容 | 相關方法已直接提供，仍選不出能區分競爭解釋的下一步 | 方法內容不夠可操作 |
| Q4 承接 | 修正後的判斷有沒有進入下一輪會讀到的條目與派單；同 session 續接與新建任務是否不同 | 持久狀態或續接問題 |
| Q5 措辭 | 派單把待驗證解釋寫成前提或「是否唯一」時，下一輪是否沿用措辭、提高確定性 | 派單契約問題 |
| Q6 模型能力 | 材料、方法與工具都固定且正確後，仍反覆失敗 | 模型或配置限制的證據增強，不直接斷言能力上限 |

另回答兩個與承接直接相關的計數問題：假設升級為 supported 時，有沒有附上被取代條目以外的新證據；交回文字與工作簿條目在結論上是否一致。

## 3. 做法

### 3.1 離線核對（不用模型，工程 session 可做）

- **承接鏈重建。** 從既有 run 的 control-audit、`context.presented`（各角色每次呈現的 `included_ids`／`omitted_ids`）、工作簿 sqlite 與派單參數，對每個假設升級、交回與 Solver 派單記錄：當時呈現了哪些條目、升級是否帶新 ref、交回與條目是否一致（關鍵詞布林值）、派單是否引用問題 id、是否帶 `task_id`。範圍是已有工作簿的 run：r1–r3、冒煙、配對批次開啟組與 runtime-diag 兩批。回答 Q1、Q4 與兩個計數問題。
- **接口核對。** 對照 design 與實作，列出各角色在決策點能看到什麼：Coordinator 視圖白名單、Critic 只收摘錄、續接與新建任務的上下文差異、已載入 Skill 在新 session 中的狀態。回答 Q1 的「設計上就看不到」部分。
- **合成案例。** 為 Q3–Q6 各準備少量無害合成決策點：給定材料與工作簿狀態、一個預期能區分解釋的下一步、不應得出的結論。先人工自檢預期是否可判定；判定不了的案例不進入模型對照。

### 3.2 需要模型的最小對照（另行授權，只用合成案例）

每組只改一個條件，其餘相同，每格至少重複數次，記錄選出的下一步是否符合預期、工作簿條目狀態與措辭沿用。

| 要區分 | 只改這一項 |
| --- | --- |
| 方法發現失敗（Q2） | 只有可用方法索引，或直接提供相關方法內容 |
| 方法內容不足（Q3） | 相關內容已提供時，用現有內容或補齊後的內容 |
| 承接失敗（Q4） | 同一修正結果，經同 session 續接或新建任務傳遞 |
| 措辭偏向（Q5） | 中立問題，或預設結論／「是否唯一」的派單 |
| 模型能力（Q6） | 材料、方法、工具全部固定，只換模型或思考設定 |

**執行方式（2026-11-18 選定丙）。** 甲（launcher 起單一角色）有兩個缺口：工作簿條目按 `run_id` 存取，新 run 無法預先寫入；launcher 只以 Coordinator 為主角色啟動。乙（直接拼接提示呼叫 provider）繞過 host 呈現，Q1、Q4 的結論不可外推。選丙：保留角色檔、Skill、CTF plugin 與工作簿視圖函式，只把 launcher 換成本地假控制服務。

- **腳本：** `tests/manual/fixed-point-harness.mts`，案例檔在 `tests/manual/fixed-point-cases/`。一次跑一個案例的一個變體；輸出目錄必須在倉庫外。
- **與 runtime 相同：** 產品資產按 launcher 的白名單複製；工具名稱、說明與參數來自真實 plugin；工作簿用 host 的 `workbookView` 組視圖，經 plugin 的 `context.prepare` 路徑附在請求中；寫入按欄位、狀態與「只取代自己角色的有效條目」檢查；工具准入沿用產品 `opencode.json` 的角色權限，`read` 只允許 Skill 根目錄。
- **與 runtime 不同：** 角色被直接提示（模式改為 all），不經 Coordinator 的 task；context 只帶 `current_question`、空的 `state.publications` 與工作簿，沒有索引摘要、最近步驟與經驗；工作簿變化時整份重送，不送 delta；`job.run`、`http.request` 等不執行，回固定的「本決策點不執行，請記錄計畫步驟並交回」或案例指定的固定結果。這些差異讓結論只適用於「給定工作簿與派單時選哪一步、寫什麼條目」，不外推到整題。
- **用量控制：** `--max-model-calls`（預設 40）與 `--timeout-ms`（預設 10 分鐘）；真實模型須同時給 `--opencode-config` 與 `--allow-model`，缺一即拒絕。
- **無模型自檢（`--mock`）：** 本地腳本化 provider，0 次模型呼叫；檢查角色提示、共用規則、工作簿 context 與派單抵達請求，管理工具與 Skill 可見，工作區讀取與 Skill 呼叫被記錄，上一輪寫入在下一輪第一個工具呼叫前可見（同 session 與新建各測一次）。7 個案例都至少跑過一個變體，10 項檢查全部通過；確定性測試 835 項與 typecheck 通過。

### 3.3 合成案例

只用本地、無害的材料；每例的預期下一步與「不應得出」都可人工判定。同一案例在不同對照中只改 §3.2 表中的一項。案例檔各帶變體：方法對照用 `index-only`／`method-provided`（或 `skill-named`），承接對照用同 session 與新建，措辭對照用 `neutral`／`presumptive`。「修正未寫回」的第一輪由模型實際執行，第二輪的結論要按第一輪有沒有改條目分開看。

| 案例 | 材料與狀態 | 預期下一步 | 不應得出 | 用於 |
| --- | --- | --- | --- | --- |
| 引號內換行 | 同一 CSV 經兩個版本的解析器得到不同行數；工作簿只有事實「行數不同」 | 用只含一行引號內換行的最小樣本分別解析，比較方言設定 | 檔案損壞、資料遺失 | Q2、Q3、Q6 |
| 日期偏一天 | 格式轉換後部分日期早一天；材料含輸入樣本與轉換設定 | 用 UTC 午夜與非午夜兩筆輸入對照，區分時區與格式符號 | 來源資料錯誤 | Q2、Q3、Q6 |
| 捨入差異 | `round(2.5)` 得 2，程式預期 3 | 查語言文件的捨入規則，用 2.5、3.5 最小重現 | 解釋器缺陷 | Q3、Q6 |
| 修正未寫回 | 工作簿假設 H1 為 open；上一輪交回文字說最小樣本已否定 H1、改提 H2，條目未改 | 先以已排除路線取代 H1、寫 H2，再沿 H2 實驗 | 把 H1 升級為 supported，或沿 H1 繼續 | Q4（同 session 與新建各一） |
| 本地權限拒絕 | 讀本地暫存檔得 `PermissionError`，執行身份與檔案權限位未知 | 並列存取控制與其他層，提出最小缺失證據；可載入 `python-runtime-diagnosis` | 部署錯誤、整體不可解 | Q2、Q4 |
| CI 失敗本地通過 | 同一測試在 CI 失敗、本地通過；派單甲問「哪一層造成、還缺什麼證據」，派單乙問「CI 環境不一致是否為唯一解釋」 | 並列依賴版本、時區、並行三種解釋，選一個最小區分 | 「唯一解釋」並升級為 supported | Q5 |
| 解碼錯誤 | `UnicodeDecodeError`；派單甲中立，派單乙要求「確認檔案已損壞」 | 檢查實際 bytes 與宣稱編碼 | 檔案損壞 | Q5 |

## 5. 驗收

- **離線部分：** 範圍內每個決策點都有結構化記錄；Q1、Q4 與兩個計數問題各有答案或 unknown，並附證據位置；合成案例各有預期判斷與不應得出的結論。這只說明哪一層可疑，不證明模型行為。
- **模型對照：** 只有在離線部分指出值得比較的層時才申請；每組結論寫明條件、重複次數與不確定性，單格少量樣本只稱方向。
- 結論回寫本文與對應 design 章節；驗證 plan 在結論轉入後刪除。

## 7. 模型對照結果

**結論。** 16 個組合各 3 次、共 48 次執行（`f7e90810` 的腳本與案例，deepseek-v4.1-flash、Solver 開思考）：0 次腳本失敗、超時或預算拒絕，2 次 `read` 因超出 Skill 目錄被拒；每次都有工具呼叫與工作簿寫入；模型呼叫 455 次，token 未取得，記 unavailable。**Q2–Q5 都沒有達到「成立」。** 最值得追的是 Q4：同 session 續接時，第二輪常不更新工作簿，與 §6 離線核對的方向相反。`job.run` 等由 harness 固定不執行，所以判的是選出的下一步與工作簿寫入，不是執行結果；單人評審，逐次理由沒有保存，只留每格計數（[gate](../../gates/fixed-point-20261118/summary.json)）。

| 問題 | 組合（各 3 次） | 結果 | 能說明什麼 |
| --- | --- | --- | --- |
| Q2 發現 | local-permission index-only／skill-named | 兩邊都 3/3 載入 `python-runtime-diagnosis` 並讀 Reference | 合成情境下沒有重現「方法可用但沒載入」 |
| Q2／Q3 | csv-quoted-newline index-only／method-provided | 符合 0/3 對 2/3 | 提供「單筆引號內換行的最小樣本」後 2/3 照做；只是方向 |
| Q3 | date-off-by-one index-only／method-provided | 符合 2/3 對 3/3 | 兩邊多數都選到午夜／正午對照，差距不足 |
| Q3 | round-half-even index-only／method-provided | 兩邊 0/3 符合（皆部分符合）；method-provided 3/3 誤載入 `python-runtime-diagnosis`，index-only 0/3 | 兩邊都提出 2.5／3.5 最小重現、沒查文件；方法文字裡的「解釋器缺陷」讓與運行時失敗無關的情境也載入了該 Skill |
| Q4 承接 | correction-not-written same-session／new-session | 第一輪 3/3 以已排除路線取代 H1；第二輪以取代更新自己的條目：same 1/3、new 3/3；same 另有 2/3 只新增不關聯的條目 | 修正有寫回；但同 session 的下一輪較常讓工作簿停在舊狀態或出現重複 |
| Q4 承接 | local-permission resume-same／resume-new | 答案 3/3 都符合；第二輪寫入：same 3/3 一條都沒寫，new 3/3 以取代更新 | 同上方向：同 session 倚賴對話歷史，新建 session 把工作簿維護好 |

| Q5 措辭 | decode-error neutral／presumptive | 兩邊 3/3 符合；presumptive 3/3 否定「檔案已損壞」，1/3 把這個否定記成 supported | 預設措辭沒有被採納 |

**Q2 與 Skill 觸發。** 未被點名時，`local-permission` 仍 3/3 載入並讀 Reference，所以合成情境裡不是發現失敗；[B §7.2](2026-10-26-design-v1-b-method-generalization-and-efficiency.md#72-python-运行时阻断归因) 的真實 run 不載入，較可能與任務中途的長上下文有關，本批無法驗證。反方向的誤觸發出現了：round 的 method-provided 3/3 載入同一 Skill，是 B §7.2 列為代價的「不相關情境也被點名」的第一個實例；目前只記錄，不改 description。

**Q3。** 只有 csv 有 2/3 方向；date 差 1/3、round 差 0/3。round 兩變體缺的是查文件與執行，本 harness 都不提供，不能寫成方法內容不足。因此不據此補 [B §7](2026-10-26-design-v1-b-method-generalization-and-efficiency.md#7-方向与优先序) 第 3 項。

**Q4（與離線核對相反，並列）。** 合成情境裡，同 session 續接的第二輪 6 次中只有 1 次以取代更新自己的條目，3 次一條都沒寫、2 次只新增不關聯的條目；新建 session 6/6 以取代更新。§6 的離線統計則是續接時上一輪條目被取代的比例較高（10/16 對 6/15）。兩者條件不同：離線樣本的續接集中在少數 run、由 Coordinator 選擇；合成樣本的第二輪派單沒有要求更新條目。這對 `eb5743d3` 的「預設續接」有直接影響：續接保住了角色自己的上下文，但 Coordinator 與下一個角色讀的是工作簿，工作簿不更新時承接只發生在單一 session 內。先不改規則；下一步是查真實 run 中續接回合交回前有沒有更新條目（`domain-solver.md` 已要求），再決定要不要在續接派單中明確要求。

**Q5。** 兩個案例的 presumptive 派單都沒有把結論推過去：交回 6/6 明確否定預設，被記成 supported 的 2 次中，1 次是否定本身（decode），1 次是在環境因素內收斂到 locale 並寫明仍需驗證（ci）。後者正是 [團隊決策 §6.2](2026-11-07-design-v1-team-decision-context.md#62-派單與交回的內容契約)「supported 不表示其他解釋已排除」的樣本，只記錄，不改契約。

**案例缺陷。** `ci-only-failure` 的 `test_report.py` 呼叫了未定義的 `label()`，照理應報 NameError，與 log 的 AssertionError 不符；兩組回答都抓到這點並轉去追「原始碼與 log 不一致」，削弱了這一格的措辭對照。案例檔已補上 `label()` 的定義（本批用的是補之前的版本），之後重跑以新版為準。
