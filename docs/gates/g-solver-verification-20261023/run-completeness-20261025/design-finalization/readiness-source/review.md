# R1 独立只读复核

日期：2026-10-25。复核范围：主区 AGENTS.md、CLAUDE.md、当前详细 design §1.1／1.2／5.1，R1 report.md 与 read-hashes.json，以及报告白名单中的 Dockerfile、两份 compose、prepare.sh、serve.py。未访问答案、oracle、README Solution、DB、原始 reasoning；未运行目标、HTTP、Docker、模型、测试或产品实现；只写本 review.md。主区已有 dirty 改动，未修改。

## 结论

**证据陈述无阻断问题；“Throwback 可信 ready 尚未成立”成立。将此直接推广为“通用 readiness 契约无法设计定稿”依据不足，应修正因果与阻断范围。当前用户约定的整体验证尚未完成，因此仍不能宣称整份设计定稿。**

### 阻断：Throwback 成功路径与既定整体验收仍缺证据

当前 §5.1 明确要求 required 缺 seed、仅端口通、有效准备、实例／版本变化和 NA 的矩阵，且 §1.1 要求整份设计先验证定稿。R1 没有成功 ready 生产者、权威成功判据与实例绑定，也没有有效样本／重建验证，不能完成这项已定验收。报告正确保留 unknown，没有用端口通、建表、脚本存在或随机数据生成结构冒充成功准备；没有理由批准 Throwback 真实 run。

静态启动白名单直接支持“本地声明的启动链没有显式 seed／可信准备记录入口”：Dockerfile 的 CMD 为 serve.py，serve.py 调 create_app 后启动，compose 没有额外准备命令，prepare.sh 只安装依赖。该结论不能外推到完整镜像、外部部署流程或其他版本。populate.py 仅经结构投影，足以证明存在脚本，不足以决定它应不应该执行、是否属于题目预期状态或是否与 judge 一致。R1 对这些边界的表述适当。

### 非阻断但需收敛：缺输入不等于通用机制不可设计

R1 缺失列表混合了两类责任，应拆开解释：

- 题目事实：Throwback 权威准备入口／seed revision／成功判据／材料关系／是否需 judge 绑定。这些影响该题适配与真实 ready 验收，不能由程序或审查人猜测。
- 产品契约：谁能写准备记录、host 如何读与验真、实例 generation／reset epoch 如何失效、required／NA 的声明语义。这些是本设计本来就要决定的接口责任；未找到现成约定并不证明必须由外部维护者先提供完整设计。

通用方案可以明确 host 信任边界、准备记录的必要绑定与失效原则，以及没有可信适配器时 required→unknown→禁止模型准入的行为；再把题目事实作为适配器输入。这样可定通用契约，不需伪造 Throwback ready，也不要求当前所有题都提供记录。不同题目的 judge 非秘密身份是否是 readiness 必要绑定，应给出需求依据与适用语义，不能仅因本题缺 controller-side oracle 就推定所有 readiness 都必须等 oracle 完备。

但这只是可继续设计的路径，**不是降低现有验收或代用户排除 Throwback**。现行 §1.1／1.2 把该题成功矩阵纳入整体定稿前提，故当前整份设计仍未满足自己的完成条件。若要将“通用机制定稿”和“Throwback 适配验收”分层，需在主设计明确目标与交付含义，并由用户决定任何实质验收变化；不能通过改名、留 unknown 或写通用样例暗中算通过。

## 建议回写

1. 保留 R1 的真实状态：Throwback readiness unknown，A/B 均未得到可采纳的该题成功来源，本轮无成功 ready 样本。
2. 将“R1 是整体 blocker”改为“既定 Throwback 成功验收未满足，按当前 §1.1／1.2 阻止整体验证完成”；避免声称静态材料缺口证明通用契约本身无法设计。
3. 继续已授权的通用契约收敛与 R2/R3，不把缺失的产品接口决定全部列为必须由用户提供的外部输入。对真正缺失的题目权威事实提出最小请求：认可的准备动作／revision、非秘密成功语义、与材料及适用 judge 的对应。实例／reset 可信 generation 的实现归属由产品与部署接口共同确定。
4. 若保留当前整体目标，成功样本与失效矩阵仍为未完成项；若拟调整验证层级，明确提出代价与待决项，不自动排除 readiness 或 Throwback。

本 review 未独立复现 create_app 内部初始化或 populate.py 安全投影，相关细节仅按 R1 报告及其 hash 索引评价，不把 hash 清单当作当前运行状态证明。

## 补充：用户确认与下一步职责

主会话转达的新增用户确认：**认可的准备脚本／说明尚不存在**。这是用户提供的现状事实，不是本次静态检查独立证明的全局不存在结论；也不构成执行 populate.py、改变题目内容或增加真实运行预算的授权。

最小下一步是先明确“准备后应当是什么”，再决定如何准备。题目维护方需确认权威题目／材料版本、该版本本应具备的数据状态、populate.py 是否属于认可准备动作，以及不泄密的成功判据；若现有材料无法确认这些事实，应先核实原始题目发布／部署来源，不能从当前空表或脚本结构倒推答案。

我们可以在现有详细 design 中设计可信准备责任、required／NA／unknown 语义、host 读取的非秘密成功记录、实例／材料／准备版本绑定与 reset 失效规则；确认题目事实后，再将最小初始化动作与只读检查接入现有部署／prepareRun 路径。准备动作应由可信部署方执行，Solver 只接收必要 readiness 事实，不能自写 ready 自证。无需为此新建自动 seed 框架，也不把“规范已写好”当作 Throwback 成功准备已验证。

当前不直接运行 populate.py。通用契约可继续收敛；该题认可准备动作和真实有效 ready／失效矩阵仍需后续取得证据，按现行整体完成条件保持未完成。若初始化确需新授权或调整既定验收，应由主会话明确提出具体动作与影响。本补充未进一步探索或读取文件。
