# code-audit-main 全貌分析

## 项目定位

`参考项目/code-audit-main` 是一个面向 Claude Code 的白盒代码安全审计 skill。它不是传统 SAST 工具，也不是单条提示词，而是一个“技能入口 + 执行状态机 + 分层知识库 + 报告模板”的组合。

它的主要目标是让 LLM 在阅读项目源码时减少随机性，按固定阶段完成：

1. 识别项目结构、语言、框架、入口点和攻击面。
2. 根据项目类型和攻击面拆分多个审计 Agent。
3. 按不同漏洞本质选择不同审计策略。
4. 并发执行第一轮广度扫描。
5. 汇总覆盖缺口，启动第二轮增量补漏。
6. 经过覆盖率、严重度、去重、报告门控后输出攻击者视角报告。

## 顶层文件职责

| 文件 | 职责 | 对本项目的启发 |
|---|---|---|
| `README_CN.md` | 面向用户的能力说明和使用方式 | 我们需要一份中文能力说明，把灰盒/白盒/浏览器动态测试边界讲清楚 |
| `SKILL.md` | Skill 入口与执行控制器 | 我们的 skill 不能只写能力描述，必须写模式选择、加载规则、暂停点和报告门控 |
| `agent.md` | Deep 模式的权威执行状态机 | 我们的 `AGENT.md` 应该成为运行时权威规则，而不是泛泛的角色设定 |
| `references/` | 审计知识和可执行检查素材 | 我们需要把知识库拆成 core、skills、adapters、cases、reporting，而不是堆文档 |

## 目录分层

`references/` 的分层很清楚：

| 目录 | 内容 | 运行时角色 |
|---|---|---|
| `core/` | 方法论、污点分析、数据流、验证、误报过滤、PoC、动态审计、覆盖追踪 | 通用执行方法，所有语言共享 |
| `checklists/` | 覆盖矩阵和语言维度提示 | 审后自检和补漏，不是主扫描逻辑 |
| `languages/` | Java、JavaScript、Python、Go、PHP 等语言级漏洞模式 | 技术栈识别后按需加载 |
| `frameworks/` | Spring、Express、Django、FastAPI 等框架专项 | 框架识别后补充高危模式 |
| `security/` | API、认证授权、业务逻辑、前端、GraphQL、跨服务信任等专项 | 按攻击面激活的横向安全专题 |
| `adapters/` | Java/JS/Python/Go/PHP 的 YAML 控制检测模式 | 把“应该存在的安全控制”映射为可搜索模式 |
| `wooyun/` | 真实漏洞案例与绕过技巧 | 静态审计后的黑盒/灰盒验证向量库 |
| `reporting/` | 攻击者视角报告模板 | 最终报告组织方式 |

## 核心审计维度

项目使用 D1-D10 作为安全覆盖矩阵：

| 维度 | 主题 | 默认策略 |
|---|---|---|
| D1 | 注入 | sink-driven |
| D2 | 认证 | config-driven / control-driven |
| D3 | 授权 | control-driven |
| D4 | 反序列化 | sink-driven |
| D5 | 文件操作 | sink-driven |
| D6 | SSRF | sink-driven |
| D7 | 加密 | config-driven |
| D8 | 配置 | config-driven |
| D9 | 业务逻辑 | control-driven |
| D10 | 供应链 | config-driven |

最重要的设计不是 D1-D10 本身，而是它没有把所有漏洞都当成 grep 问题：

- `sink-driven`: 搜索存在的危险调用，如 SQL 拼接、命令执行、反序列化、文件操作、SSRF。
- `control-driven`: 枚举应该受保护的端点/操作，再验证安全控制是否存在，如授权、IDOR、业务逻辑。
- `config-driven`: 搜索配置和依赖，再与安全基线比对，如 JWT、CORS、加密算法、Actuator、依赖版本。

这个三轨模型非常适合本项目。灰白盒渗透测试里，浏览器动态测试发现的是“可达攻击面”，白盒代码审计发现的是“实现风险”，两者都需要用同一套维度和策略归档。

## 运行模式

项目定义 Quick、Standard、Deep 三类模式：

| 模式 | 特征 | 适用场景 |
|---|---|---|
| Quick | 只做一轮，覆盖优先，报告中标注未覆盖项 | 小变更、快速审查 |
| Standard | 1-2 轮，R2 至少做一次补漏或深挖 | 常规项目审计 |
| Deep | 2-3 轮，强制 R2，必要时 R3 构建攻击链 | 完整安全评估 |

`SKILL.md` 还规定了一个很重要的暂停点：完成模式判断、文档加载、侦察和计划后必须停止，等待用户确认再执行。这对渗透测试 Agent 很重要，因为未授权范围、账号权限、测试窗口、生产环境边界都必须在执行前确认。

## 全貌评价

`code-audit-main` 的优点：

- 用状态机降低 LLM 随机执行。
- 用覆盖矩阵阻止“扫到几个漏洞就写报告”。
- 用 Agent Contract 限制每个子 Agent 的搜索路径、预算、输出格式。
- 用 R2 增量约束减少重复搜索。
- 用 `adapters/*.yaml` 把通用安全控制落到具体技术栈。
- 用 WooYun 案例把白盒发现转化为可验证的攻击路径。

主要不足：

- 它更偏白盒静态审计，浏览器动态测试、API 自动调用、会话态管理、代理流量记录不是主线能力。
- 它的工具执行仍以 LLM 约束为主，缺少本项目已有 harness 这种可验证的机器执行层。
- 部分知识文件非常大，实际运行时如果不做路由和片段加载，容易造成上下文浪费。

对本项目的定位建议：

我们不应直接复制它的所有文档，而应复制它的“控制结构”：入口控制器、状态机、Agent Contract、覆盖矩阵、跨轮传递字段、技术栈 adapter，再把浏览器/API 动态测试和灰盒资料学习接到同一个状态机里。
